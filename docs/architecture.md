# Архитектура бэкенда системы рекомендаций

Решение: отдельный Python-сервис с HTTP API на FastAPI. Архитектура строится на DDD с разделением слоёв domain, application, port, adapter, presentation и di. Реализованы профили, каталог фильмов и сериалов и импорт метаданных из TMDB. Оценки и избранное сохраняются по профилям. Рекомендации обслуживает адаптер обученной item-based модели.

## Слои и зависимости

```text
src/
  config/
    settings.py           # настройки окружения и их валидация
    paths.py              # пути проекта
  domain/
    entities/
      profile.py          # сущность Profile и её инварианты
      movie.py            # фильм или сериал с внутренним UUID
      genre.py            # жанр в контексте типа контента
      rating.py           # оценка профилем фильма: целое 1–5
      favorite.py         # независимая связь профиля с фильмом
    value_objects/
      media_type.py       # movie и tv
    exceptions/
      base.py             # DomainError
      profile.py          # нарушение ограничений профиля
  application/
    base_interactor.py    # общий интерфейс сценария
    command/              # сценарии изменения данных
    query/                # сценарии чтения
    dto/                  # входные данные и результаты сценариев
    service/              # запись импортированной пачки каталога
    exceptions/           # ошибки выполнения сценариев
  port/
    repositories/         # интерфейсы доступа к доменным сущностям
    clock.py
    id_generator.py
    database_probe.py
    movie_metadata.py     # контракт внешнего источника и его dataclass DTO
    exceptions/           # ошибки внешних портов
    unit_of_work.py
  adapter/
    database/
      models/             # ORM-модели
      converters/         # преобразование ORM и доменных сущностей
      repositories/       # реализации репозиториев
      engine.py
      migrations.py
      database_probe.py
      unit_of_work.py
    tmdb/                 # HTTP-адаптер и DTO ответов внешнего API
    system/               # системные часы и генератор UUID
  presentation/
    http/
      dto/                # Pydantic RequestDTO и ResponseDTO
      routers/            # маршруты FastAPI
      exception_handler.py
  di/
    providers/
      configuration.py    # Settings
      database.py         # engine, сессии, транзакции, проверка готовности
      repositories.py     # репозитории
      metadata.py         # HTTP-клиент и TMDB-адаптер
      system.py           # Clock и IdGenerator
      interactors.py      # обработчики команд и запросов
    container.py
  main.py                 # сборка приложения и управление его жизненным циклом
```

Domain не импортирует FastAPI, SQLAlchemy или ML-библиотеки. Application зависит от domain и port. Адаптеры реализуют порты; HTTP-обработчик переводит запрос в DTO и вызывает интерактор. Dishka собирает зависимости. Команда завершает транзакцию через UnitOfWork; запрос не делает commit.

## Соглашения по структуре

Сущности размещаются в `domain/entities`, бизнес-исключения — в `domain/exceptions`. Ошибки поиска и выполнения сценария принадлежат `application/exceptions`: например, отсутствие профиля при чтении — это `ProfileNotFoundError` уровня приложения. Доменные сущности не содержат правил HTTP или работы с ORM.

DTO разделены по назначению. `application/dto` содержит независимые от фреймворка dataclass для команд, запросов и результатов сценариев. `presentation/http/dto` содержит Pydantic-модели HTTP-запросов и ответов с суффиксами `RequestDTO` и `ResponseDTO`; они отвечают за валидацию и сериализацию на границе API. Роутер преобразует HTTP DTO в данные сценария и его результат обратно в ResponseDTO.

`presentation/http/exception_handler.py` содержит именованные обработчики исключений и их регистрацию. Формат ошибки описан отдельным HTTP DTO. Application и domain не формируют JSON-ответы и не выбирают HTTP-статусы.

Настройки явно импортируются из `config/settings.py`, пути — из `config/paths.py`. DI-провайдеры разделены по ресурсам и назначению, а состав контейнера задаётся в `di/container.py`. Модуль `main.py` остаётся точкой сборки приложения.

## Реализованная основа

`main.create_app` создаёт FastAPI-приложение и DI-контейнер без изменения схемы БД. Dishka управляет временем жизни ресурсов: engine и фабрика сессий существуют в рамках приложения, AsyncSession — в рамках запроса. Репозиторий и UnitOfWork одного запроса получают одну сессию. При завершении запроса сессия закрывается и откатывает незавершённую транзакцию; при остановке приложения контейнер освобождает engine.

Профиль — самостоятельная доменная сущность с UUID, отображаемым именем и временем создания. Создание выполняется командой CreateProfileHandler, чтение — запросами GetProfileHandler и ListProfilesHandler. Домен не зависит от Pydantic; HTTP-модели и ORM-модели находятся во внешних слоях.

Миграция `0001_profiles` создаёт таблицу profiles. Ограничение длины имени действует в домене, HTTP-валидации и БД. Временные отметки записываются в UTC; при чтении SQLite восстанавливается часовой пояс. Внешние ключи включены для каждого подключения, транзакциями SQLite управляет SQLAlchemy.

`/health` проверяет процесс без обращения к БД. `/ready` проверяет доступность БД, совпадение ревизий Alembic с миграциями приложения и наличие необходимых таблиц и ключевых полей профилей и каталога. Отсутствующая или устаревшая схема даёт HTTP 503. Готовность модели отражается отдельно: `not_configured`, `ready` или `unavailable`. Отсутствие настройки не блокирует остальное API; ошибка загрузки артефакта отражается в model, но не блокирует готовность БД и остальных источников.

## Каталог и импорт

`Movie` хранит внутренний UUID, TMDB ID, тип контента, метаданные, жанры и время последнего обновления. Уникальная внешняя идентичность — `(media_type, tmdb_id)`. `movie:123` и `tv:123` различаются; анимация является жанром фильма. `movielens_id` зарезервирован для будущего импорта MovieLens и допускается только у фильмов.

Миграция `0002_catalog` создаёт `movies`, `genres` и `movie_genres`. Жанр идентифицируется парой `(media_type, tmdb_id)`. Составные внешние ключи не позволяют связать фильм с жанром другого типа контента. При повторном импорте выполняется upsert по внешней идентичности: UUID и MovieLens ID остаются прежними, связи жанров заменяются актуальными.

Команды `ImportCatalogHandler` и `ImportMovieHandler` обращаются к порту `MovieMetadataProvider`. Адаптер `TMDBMovieMetadataProvider` использует HTTPX2 и проверяет ответы через собственные Pydantic DTO в `adapter/tmdb/dto.py`. Эти модели не используются как DTO приложения или HTTP API нашего сервиса.

Внешние запросы завершаются до начала записи в БД. `CatalogWriter` сохраняет всю полученную пачку в одной транзакции; при ошибке записи откатываются и новые фильмы, и изменения существующих фильмов и жанров. Он вызывается только командами импорта. `ListMoviesHandler` и `GetMovieHandler` читают БД через порт репозитория и не вызывают commit.

Поиск выполняется по нормализованному через casefold полю русского и оригинального названий, включая кириллицу. Символы SQL LIKE экранируются. Локальные результаты фильтруются по типу и жанру, сортируются по популярности TMDB и UUID и возвращаются с пагинацией и точным количеством локальных совпадений. Популярность не является персональной оценкой модели.

Недоступность TMDB блокирует внешний просмотр без свежего кэша и сохранение ещё не загруженных карточек. Уже сохранённый каталог и `/ready` от неё не зависят. Отсутствие ключа даёт 503 для команды импорта; ошибки источника — 502; неизвестный внешний или внутренний фильм — 404. URL запросов с ключом не включаются в ответы об ошибках.

## Первая версия предметной модели

Movie хранит внутренний ID, тип контента и внешние ID TMDB/MovieLens. Profile хранит предпочтения отдельного пользователя; ID из MovieLens не становятся профилями пользователей приложения. Rating связывает профиль и фильм; одна актуальная оценка 1–5 на пару, с датой изменения. Favorite хранится независимо от Rating: добавление в избранное не означает положительную оценку.

Анимация — жанр фильма. Категории movies и cartoons могут ссылаться на один объект. TMDB movie:123 и tv:123 — разные объекты. Для первой ML-версии используем только фильмы, включая анимацию. Сериалы остаются доступны как каталог с оценками, но исключаются из рекомендаций модели для фильмов.

БД — SQLite через SQLAlchemy async, миграции Alembic. Операции библиотеки всегда ограничены profile_id. Проверка права доступа к профилю будет добавлена вместе с авторизацией. Текущая версия профилей предназначена для локальной разработки: переданный клиентом profile_id сам по себе не подтверждает доступ.

## HTTP API

Доступные маршруты и форматы описаны в [HTTP API](api.md). Реализованы профили, discovery, локальный каталог, импорт и библиотека профиля. Рекомендации реализованы через порт RecommendationEngine. Отдельный метод похожих фильмов пока не реализован.

## Библиотека профиля

Миграция `0003_library` создаёт таблицы favorites и ratings. Составной первичный ключ `(profile_id, movie_id)` исключает дубликаты; внешние ключи связывают действия с профилями и фильмами. Оценка — строго целое число 1–5 с временем обновления. Повторное добавление избранного сохраняет исходную дату, повторное выставление оценки обновляет значение и дату. Удаление ограничено выбранным профилем и идемпотентно.

`ChangeLibraryHandler` проверяет профиль и ограничения действия. `MovieResolver` разрешает UUID или внешнюю идентичность через локальный репозиторий, завершает фазу чтения перед сетевым запросом и загружает только отсутствующие карточки. Сохранение фильма и пользовательского действия выполняется в одной транзакции. Ошибка записи откатывает оба изменения. Уже сохранённые карточки не требуют TMDB.

`GetLibraryHandler` получает избранное и оценки вместе с карточками без запросов к источнику. Ответ — полный снимок пользовательской коллекции, без пагинации. Его загрузка выполняется при выборе профиля и обновлении интерфейса; обычное изменение возвращает одну запись. Для больших коллекций следует добавить постраничное чтение.

`ImportLibraryHandler` переносит 1–20 записей за одну транзакцию. Дубликаты внешней идентичности объединяются; серверная оценка имеет приоритет над импортируемой. Повторение не дублирует избранное. Сохранение исторического времени требует даты с часовым поясом. Фронтенд отправляет пакеты по 10 и сохраняет исходную браузерную копию; сбой следующего пакета не откатывает предыдущие.

## Рекомендации

Ответ рекомендации содержит items, strategy, model_version. score — внутренний балл ранжирования, а не вероятность или прогноз личной оценки. При нехватке оценок используем явно обозначенную базовую подборку. Уже оценённые фильмы исключаем. Обоснование рекомендации отдаём только если оно поддерживается выбранным алгоритмом.

## Обучение и применение модели

Обучение — отдельный offline-процесс: загрузка и фиксация датасета, подготовка, разбиение, сравнение алгоритмов, сохранение модели и метрик. В артефакте должны быть mapping внутренних индексов, версия каталога, конфигурация и версия формата. HTTP-сервис не обучает модель на каждый запрос. Адаптер рекомендаций один раз загружает совместимый артефакт и реализует порт.

Для нового профиля нельзя использовать случайный userId из обучающего набора. Item-based модель строит результат из реальных оценок профиля; факторизация требует вычисления представления нового пользователя по его оценкам. Этот сценарий должен проверяться отдельно.

## Переход с текущего фронтенда

Next.js получает каталог в серверном модуле `src/moviesApi.ts`, а библиотеку — через Server Actions. Zustand хранит только экранный кэш коллекции выбранного профиля. В localStorage запоминается UUID профиля; прежние локальные записи доступны для явного переноса. Бизнес-правила и ML остаются в Python-сервисе.

Внешние карточки используют TMDB ID без UUID; сохранённые карточки имеют UUID и отдельный TMDB ID. Числовые ссылки открывают внешний просмотр без импорта; UUID-ссылки читают сохранённую карточку.

## Просмотр внешнего каталога и кэш

Основной поиск интерфейса выполняют DiscoverMoviesHandler и DiscoverMovieHandler. Они зависят только от порта метаданных, не читают репозитории фильмов и не запускают транзакции. Ответ discovery содержит внешнюю идентичность без локального UUID.

APP-scoped CachedMovieMetadataProvider декорирует TMDB-адаптер. Два LRU-кэша хранят успешные страницы и карточки: до MOVIE_TMDB_CACHE_ENTRIES записей в каждом, TTL задаёт MOVIE_TMDB_CACHE_TTL. Ключ страницы включает тип контента, нормализованный поисковый запрос, жанр и номер страницы. Ключ карточки включает тип и TMDB ID. Справочники жанров кэшируются отдельно на 86400 секунд.

AsyncTTLCache объединяет одновременные загрузки одного ключа. В каждой группе допускается до 32 ожидающих уникальных ключей и 4 выполняющихся загрузок. Превышение очереди даёт ошибку доступности. Ошибки не сохраняются в кэше. Отключение одного клиента не отменяет общую загрузку для остальных. При остановке контейнера незавершённые загрузки отменяются, затем закрывается HTTP-клиент.

Кэш находится в памяти одного процесса, сбрасывается при перезапуске и не синхронизируется между worker-процессами. Истёкшие данные не выдаются как свежие при ошибке источника. Просмотр не зависит от количества ранее импортированных записей и не увеличивает таблицы каталога.

Карточка сохраняется в БД только отдельной командой при пользовательском действии или служебном импорте. При добавлении в избранное и выставлении оценки сервис сохраняет отсутствующую карточку вместе с действием.


## Offline-процесс и подключение модели

`src/ml` содержит независимый от HTTP и БД pipeline потоковой подготовки MovieLens 32M, блочного обучения и временной проверки качества. NumPy/SciPy устанавливаются extra `ml`; API без настроенной модели не импортирует их. Артефакт содержит матрицу соседей, популярность и mapping TMDB/MovieLens, но не истории отдельных пользователей.

`port/recommendation.py` определяет контракт ранжирования. APP-scoped `ArtifactRecommendationEngine` однократно проверяет и загружает артефакт; DI-провайдер находится в `di/providers/recommendation.py`. Чтение и вычисления выполняются через asyncio.to_thread.

`GetRecommendationsHandler` проверяет профиль, читает его оценки фильмов и завершает транзакцию чтения перед вычислением рекомендаций и запросами метаданных. Никакого импорта карточек при выдаче рекомендаций нет. Метаданные берутся через общий кэш, при недоступности источника используются названия из артефакта.

Версия модели, выбранная стратегия, причина базовой выдачи и покрытие оценок профиля возвращаются в API. Методика выбора параметров и ограничения проверки качества описаны в [документации ML](machine-learning.md).


## Сборка гибридных рекомендаций

`HybridRecommender` в application/service оркестрирует независимые источники: порт RecommendationEngine для обученного артефакта и порт ContentRecommendationProvider для подбора по метаданным. MetadataContentRecommender реализует второй контракт через MovieMetadataProvider. Фреймворки и конфигурация окружения не входят в логику ранжирования; DI преобразует настройки в RecommendationPolicy.

Интерактор передаёт сервису оценки и метаданные фильмов текущего профиля после завершения транзакции чтения. Результаты источников объединяются по рангам с удалением дубликатов и оценённых фильмов. HTTP DTO отражают стратегию, происхождение элементов и частичную недоступность источников. Подробности ограничений и резервирования — в [описании рекомендаций](recommendations.md).

Режим `surprise` обслуживает отдельный `SurpriseRecommender`. Он использует методы explore портов RecommendationEngine и ContentRecommendationProvider, Clock для границ годов и RandomSeedGenerator для новых подборок. Адаптер генератора seed применяет системный источник случайности. HTTP-параметр mode выбирает сервис в интеракторе; права и границы профиля, завершение транзакции чтения и обогащение карточек общие для обоих режимов.
